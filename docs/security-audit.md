# Security Audit

Status: **complete** (2026-09-24). A full pass across authentication, authorization, RBAC, session handling, input validation, injection, uploads, secrets, logging, payments, webhooks, and price-integrity — plus the six specific attack scenarios named in the task. Every finding below cites real file:line evidence; nothing here is taken from the codebase's own documentation on faith. Where CLAUDE.md/architecture.md make a security claim, this audit traced that claim to the actual enforcing code and says so explicitly.

**Method.** No browser or live-traffic tool was available this session, so this is a source-code audit: four focused tracks (auth/RBAC core; route-level authorization and IDOR; input validation/injection/uploads/secrets; payments/webhooks/price-snapshot integrity) each read the real implementation — middleware, services, schemas, models — and reasoned through concrete exploit attempts rather than trusting comments or naming. `pnpm -r typecheck`, `apps/api`'s full test suite (1618 tests, +2 from this pass) and the three frontend builds are all clean after the fixes below.

**Headline result.** This audit found **no Critical or High-severity vulnerabilities**. All six scenarios the task asked to specifically verify are **blocked**, each with a concrete code citation and, in every case, an existing automated test proving it. Four Low-severity findings were identified; two were fixed in this pass (webhook rate limiting, refresh-failure audit coverage), and two are documented with rationale for why they weren't force-fixed.

## The six scenarios, verified

| # | Scenario | Verdict | Evidence |
|---|---|---|---|
| 1 | A malicious B2C user cannot change price | **BLOCKED** | `packages/validation/src/checkout.ts:29,35` — `placeOrderSchema`/its line schema are `.strict()` zod objects with no price/discount field at all; sending `unitPrice` in a line is a 400, not silently dropped. Every priced field on the `Order` (`unitPrice`/`lineTotal`/`taxableValue`/`gst`) is written from `packages/pricing-engine`'s server-computed `PricedDesign`, never from `req.body` (`apps/api/src/modules/orders/checkout.service.ts:257-276`). `agreedTotal` is compared against the server total and aborts the order on mismatch (`checkout.service.ts:217`, `PriceChangedError`) — it is never used to *set* a price. Tested: `apps/api/src/http/checkout.routes.test.ts:138` (`unitPrice` in the body → rejected), `:218` (a direct `OrderModel.updateOne` on an existing line price is rejected by the append-only/immutable-order-paths guard). |
| 2 | A B2B user cannot access another B2B customer's orders | **BLOCKED** | Every portal read is scoped server-side by the caller's own `customerId`, resolved from the DB (`requireBuyer`, `apps/api/src/http/middleware/require-buyer.ts:13-19` — looks up `UserModel.findById(req.auth.userId)`, never trusts a client-supplied id), then baked into the Mongo filter itself (`apps/api/src/modules/b2b/b2b-reads.service.ts:22,41-46,59-66,79-84,94-99,101-106` — `Model.findOne({_id: id, customerId})`, so a wrong id for the caller's own customer is indistinguishable from a nonexistent document — `NotFoundError`, not a 403 that would confirm the id is valid). Same pattern in `apps/api/src/modules/b2b/procurement.service.ts:96-101,220-225` (`ownPo`/`ownQuotation`). Tested: `apps/api/src/http/b2b.routes.test.ts:177` ("gives a buyer only their own documents — another customer's are simply not found") and `:1022`. |
| 3 | A normal employee cannot bypass approval workflows | **BLOCKED** | Every maker-checker flow gates creation and approval on two *different* permission constants: inventory adjustment (`INVENTORY_ADJUST` to request vs. `INVENTORY_APPROVE_ADJUSTMENT` to approve, `apps/api/src/http/routes/inventory.routes.ts:70-72`), manufacturing QC (`PRODUCTION_CREATE` vs. `PRODUCTION_APPROVE`, `manufacturing.routes.ts:33-53`), procurement PO (`PURCHASING_CREATE` vs. `PURCHASING_APPROVE`, `purchasing.routes.ts:43-45,70-73`), B2B credit override (`B2B_APPROVE_PO`+`B2B_OVERRIDE_CREDIT`, checked at both the route *and* again inside the service, `b2b-admin.routes.ts:31`, `procurement.service.ts:372`). Inventory adjustments go further: the requester is blocked from approving their *own* request even while holding the approval permission (`apps/api/src/modules/inventory/inventory.service.ts`, tested at `inventory.routes.test.ts:554`). Tested: `manufacturing.routes.test.ts:84` (QC pass without `PRODUCTION_APPROVE` → 403), `inventory.routes.test.ts:554` (self-approval blocked). |
| 4 | A frontend request cannot directly modify inventory | **BLOCKED** | The only endpoint that patches an `InventoryItem` outside the ledger is `PATCH /api/inventory/items/:id/identifiers` (`inventory.routes.ts:50-54`), and its schema (`packages/validation/src/inventory-item.ts:108-113`) allows only `barcode`/`serialNumber`/`huid`/`stoneDetails` — no `quantity`/`status` key exists in the schema, so zod strips it even if a client sends it. Every quantity/status-changing operation (`receiveNewInventoryItem`, `reserveItems`, `sellItems`, `returnItems`, `movePartner`, transfers, adjustments) routes through `postInSession`/`withInventoryTransaction` (`apps/api/src/modules/inventory/inventory-transaction.service.ts:33-48`) — no raw `findByIdAndUpdate` with attacker-controlled `quantity`/`status` is reachable from any route. Tested: `inventory.routes.test.ts:404` ("cannot smuggle status, quantity, weights or ledger fields past the schema"). |
| 5 | Payment webhooks cannot be replayed | **BLOCKED** | `PaymentEventModel` has a unique compound index on `{provider, eventId}` (`payment.model.ts:107`); the handler does an atomic `findOneAndUpdate(..., {upsert:true})` and only acts on a record with no `processedAt` yet (`apps/api/src/modules/orders/payments/payment.service.ts:293-333`), so a redelivered event is a genuine no-op — not just "handled gracefully" but literally never re-executed. `settleCapture` is separately idempotent at the order layer too (`payment.service.ts:128`: `if (order.paymentId === payment.id) return "IGNORED"`), so even a *different* event id that reports the same payment captured twice can't double-credit. The reported amount is cross-checked against the order's own server-computed total before anything is marked paid (`payment.service.ts:134`). Tested extensively: `checkout.routes.test.ts:513-570` ("duplicate payment webhook" — same event twice, three concurrent deliveries via `Promise.all`, a webhook racing the customer's own return, a stale/older event arriving after a newer one, a forged signature, a tampered body). |
| 6 | Price snapshots cannot be modified after finalization | **BLOCKED** | `PriceSnapshotModel`'s schema is `.plugin(appendOnlyPlugin, {entityName:"PriceSnapshot"})` (`apps/api/src/modules/orders/price-snapshot.model.ts:28`), which blocks every mutating Mongoose op (`updateOne`/`updateMany`/`findOneAndUpdate`/`deleteOne`/`deleteMany`/`findOneAndDelete`/`replaceOne`/`.save()` on an existing doc) at the query-middleware level, throwing `ImmutableRecordError` (`apps/api/src/shared/append-only.plugin.ts:11-41`). Grepping every write site of `PriceSnapshotModel` in `apps/api/src` turns up only `.create()` calls (`checkout.service.ts:230`, `procurement.service.ts:345,437`) — never a mutation of an existing snapshot. A B2B quotation revision creates a *new* quotation version rather than editing the old one's prices (`procurement.service.ts:444`). Tested: `checkout.routes.test.ts:215-218` and `b2b.routes.test.ts:425` explicitly assert `PriceSnapshotModel.updateOne(...)`/`.deleteMany(...)` reject with `/append-only/`. |

## Full checklist

### Authentication — secure
- **Login** pays the same bcrypt cost whether the email is unknown, the account is locked, or the password is wrong (`auth.service.ts:81-108`, `burnPasswordCheck`), and every failure path returns the identical generic `INVALID_CREDENTIALS` error — no user-enumeration via message or timing.
- **Account lockout**: 5 failed attempts locks the account for 15 minutes (`user.repository.ts:74-79`, configurable via `MAX_FAILED_LOGINS`/`LOCKOUT_MINUTES`), independent of IP-based rate limiting.
- **Password policy** (`packages/validation/src/auth.ts:9-13`): minimum 10 characters, at least one letter and one digit, capped at bcrypt's real 72-byte limit (rejected, not silently truncated — an easy-to-miss correctness detail). No special-character mandate, which matches current NIST 800-63B guidance rather than being a gap.
- **Password reset** never confirms whether an account exists (`auth.service.ts:213-231`, `auth.routes.ts:78-81` — identical 202 either way); reset tokens are opaque, hashed, single-use, and verified before being marked used; every session is revoked on a successful reset.

### Session / JWT handling — secure
- **Access tokens**: HS256 pinned explicitly (`tokens.ts:34-45` — no `alg:none`/RS256-confusion acceptance), issuer/audience checked, carry only `userId`+`sessionId` (no roles/permissions baked in, so a stale token can't carry stale privileges).
- **Every request re-verifies the session from the database** (`auth.service.ts:181-189`), not just the JWT signature — a revoked session, a deactivated user, or a changed role takes effect on the *next* request, not at token expiry.
- **Refresh tokens** are opaque (24-hex-id + 32-byte secret), only their SHA-256 hash is stored, compared in constant time. Rotation is single-use with **theft/replay detection**: presenting an already-rotated-away token revokes the whole session and audits `SESSION_REUSE_DETECTED` (`auth.service.ts:128-134`). Rotation itself is a compare-and-swap, so two concurrent replays can't both win.
- **Logout is real server-side revocation** (`revokeSession`, `session.repository.ts:10-13`), not just a cleared cookie.
- **Cookies**: refresh token is `httpOnly`, `secure` (default true in production), `sameSite:"strict"`, scoped to `/api/auth` (`auth.routes.ts:22-28`), plus an explicit `Origin`-allowlist check on `/refresh` and `/logout` (`trusted-origin.ts`) as CSRF defense-in-depth on top of `SameSite=Strict`. The **access token is only ever in the JSON body**, never a cookie (verified: `res.cookie` is called exactly once in the whole auth router, for the refresh token only) — matches CLAUDE.md rule 10.

### RBAC / privilege escalation — secure
- `DEFAULT_ROLE_MATRIX` (`role-matrix.ts`) is the sole definition of system-role permissions; `syncRbac()` overwrites system roles from it at every boot, so a hand-edited DB row can't persist drift.
- **A caller can never grant a permission they don't themselves hold**: `assertCanGrantRoles`/`assertCanManageUser` (`authorization.service.ts:82-94`) are checked before creating a user, changing a user's roles, or editing/deactivating a user; self-escalation is separately blocked (`setUserRoles` throws on `targetId === actor.userId`, `user-admin.service.ts:47`); the general profile-patch endpoint's schema (`adminUpdateUserSchema`) has no `roleIds` field at all, so it can't be used as a side-channel around the role-grant check.
- **Zero hardcoded role-name checks anywhere outside `role-matrix.ts`/`rbac-sync.ts`** (repo-wide grep) — every authorization decision goes through `requirePermission`/`requireAnyPermission` over `ctx.permissions`, never `ctx.roles` or a role-name string comparison. This directly confirms CLAUDE.md rule 9's claim in code, not just in prose.
- Custom-role editing can't attach a permission the editor doesn't hold (`role-admin.service.ts:41`); system roles are read-only outside the matrix file.

### Rate limiting — secure, one hardening note
- Login: 20/15min per IP. Forgot/reset-password: 5/hour per IP. Storefront writes (checkout, cart quotes, returns): 30/min per IP. All configurable, all keyed on `req.ip`, which only reflects a spoofable `X-Forwarded-For` when `TRUST_PROXY=true` is explicitly set (default `false`) — an attacker can't trivially move themselves to a fresh rate-limit bucket by spoofing a header against the default config.
- **Low finding (not fixed):** the IP-based limiter has no per-account backstop independent of the account-lockout counter. A distributed, low-and-slow attack (a handful of attempts per source IP, spread across many IPs, each staying under both the per-IP rate limit and the 5-attempt lockout threshold) isn't caught by either control today. This is a real hardening gap, not an exploitable break — the account lockout is still the primary defense and does fire once 5 failed attempts land regardless of source IP. Closing it properly needs a per-account limiter (or a CAPTCHA/device-risk signal) with its own design tradeoffs; adding one blind, without a concrete incident motivating it, would be exactly the kind of unrequested abstraction CLAUDE.md's working conventions warn against — noted here for whoever owns that call.
- **Fixed in this pass:** the payment webhook route (`POST /api/store/payments/webhooks/:provider`) previously carried no rate limiter at all, unlike every other write endpoint on the same router. It's unauthenticated by design (a signature proves the sender, not a session), so this was never a trust-boundary gap — HMAC verification happens before any DB access and rejects a forged/unsigned payload outright — but an unrestricted, cheap endpoint is still a flooding vector. Added a dedicated `webhook` rate-limit rule (120/min per IP, generous enough that a provider's own legitimate retry bursts won't trip it) — see "Fixes" below.

### Input validation & injection — secure
- Every write route validates `req.body`/`req.query`/`req.params` before touching the database, via one of two consistently-applied patterns: route-level `validateBody(schema)` middleware, or a service function that calls `<schema>.parse(input)` as its first line. Spot-checked 12+ routes across 9 modules (auth, inventory, b2b, checkout, accounting, reports, purchasing, users, products) — no route found where an unvalidated field reaches Mongoose.
- **No NoSQL injection surface found**: zero `$where` usage, zero `JSON.parse(req.*)`, zero `Model.find(req.query)`/`Model.find(req.body)` wholesale-passthrough. Every `updateOne`/`findOneAndUpdate` either uses literal filters or builds its update object from an explicit, named-field allowlist derived from a zod-parsed input — never `$set: req.body` directly. Zod's default (non-`.passthrough()`) schemas strip unrecognized keys, so mass-assignment via an unexpected field name isn't possible even where a schema is broad.
- Tested: `auth.routes.test.ts:55` sends `{email:{$ne:null}, password:{$ne:null}}` to login and asserts 400 (NoSQL-injection-shape rejection).

### XSS — secure
- The API returns no HTML; the only place user-adjacent content could reach markup is B2C's JSON-LD structured data (`apps/b2c-store`, 5 `dangerouslySetInnerHTML` sites, all `<script type="application/ld+json">`), and the shared serializer escapes `<` and HTML-comment sequences before interpolation (`lib/seo.ts:62`) — and the underlying content is admin-authored catalog data, not end-user input, in any case.
- Password-reset emails only exist as a dev-mode `console.log` stand-in (`ConsoleEmailSender`); production uses `UnconfiguredEmailSender`, which sends nothing — no HTML email templating exists to have an injection surface in the first place.

### CORS — secure
- `apps/api/src/http/app.ts:69-74`: `origin` is a strict allowlist check (`config.allowedOrigins.includes(origin)`), never a wildcard or a reflected-Origin passthrough — the only correct way to pair with `credentials:true`. The env var default (`http://localhost:3000`) is restrictive, not permissive; a value like `ALLOWED_ORIGINS=*` would be treated as one literal, non-matching origin string and fail closed, not open.

### File / image uploads — secure
- Product images: size-capped via multer, identified by **magic bytes** (PNG/JPEG/WEBP signatures), never by client-declared Content-Type or extension — and **SVG is explicitly rejected by design** ("script-capable markup, not a raster image", `image-validation.ts`). Storage keys are server-generated UUIDs; the original filename never reaches disk. Serving sets `Content-Type` from the stored extension only, plus `X-Content-Type-Options: nosniff`.
- B2B PO attachments: 5MB cap, magic-byte sniffing (PDF/PNG/JPEG/XLSX/CSV only, with a NUL-byte guard on CSV), filename sanitized and length-capped, storage key regex-validated with a path-containment check. Downloads are always served `Content-Disposition: attachment` + `nosniff` — a PDF or CSV can never render inline as HTML, closing the stored-XSS-via-upload vector.

### Secrets & environment variables — secure
- `JWT_ACCESS_SECRET` is a required env var with a minimum-32-character zod check and **no fallback default** — a missing or weak secret fails boot, not silently degrades. Same for `MONGODB_URI` (required, no default connection string).
- Repo-wide grep for hardcoded-fallback-secret patterns and for real-looking API-key shapes (`sk_live`, `sk_test`, `AKIA...`, `AIza...`, `ghp_...`, PEM headers) found nothing. `.gitignore` covers `.env`/`.env.local`; the only env file ever committed is `apps/api/.env.example` with empty placeholders.
- No payment-provider integration exists in production yet (the interface is real; only a dev sandbox adapter is registered, and `apps/api/test/isolation.test.ts` fails CI if any `src/` file imports the dev-adapters directory) — so there are no live payment keys to leak today.

### Logging & sensitive data exposure — secure
- No request-logging middleware logs `req.body` or headers. The error handler logs the error object (not the request body) and returns a generic message to the client in production — no stack trace or internal detail leaks over HTTP.
- `sanitizeAuditMetadata` (`audit.service.ts:141-158`) redacts any metadata key matching `/pass(word)?|token|secret|hash|authorization|cookie|otp/i`, recursively, with size limits — and it's not opt-in per call site: `recordAudit` is the **only** place that writes to `AuditLogModel` (repo-wide grep confirms one call site outside tests), so every audit call anywhere in the codebase is automatically sanitized rather than relying on each caller to remember to.
- `toSafeUser()`/`toAuthUser()` explicitly discard `passwordHash`/lockout fields before building any response DTO, and the read query itself uses a `-passwordHash ...` projection — the hash never leaves MongoDB on a normal read, not just "gets stripped after."

### Payments, webhooks, price/checkout integrity — secure
Covered in full in the six-scenarios table above (rows 1, 5, 6) plus:
- **Verify/cancel-after-return flow** (`POST /orders/:orderNo/payments/:paymentId/verify`): the client-supplied "proof" object is passed to the *provider's* `fetchStatus`, but the reference sandbox implementation ignores it and returns the gateway's own server-side record — there is no code path where a forged client proof alone marks a payment captured. The same idempotent `settleCapture` function backs both the webhook and the verify path, so repeated verify calls never double-post accounting/inventory effects.
- **Idempotent order creation**: `Order.idempotencyKey` is a real unique Mongo index, not just a stored value; a reused key with a *different* payload is rejected (`IdempotencyKeyReusedError`) rather than silently returning the old order, and a concurrent double-submit race is handled via the unique-index violation (code 11000), not a naive check-then-act.
- **B2B offline payments**: a customer's self-reported payment always starts `PENDING_VERIFICATION` and cannot verify itself — `SelfVerificationError` fires even for a staffer verifying their own entry, and the verify/allocate/reverse routes are mounted only on the ERP side, gated by a staff-only permission the customer-portal session can't carry. An invoice's outstanding balance only ever moves from a `VERIFIED` payment.
- **B2B credit-limit check**: the only code path that creates a `SalesOrderModel` always runs the credit check inside the same MongoDB transaction as an atomic `$inc` on the customer's `creditSeq`, so a concurrent second conversion against the same customer is forced to retry and re-read the updated position — not a naive read-then-write race.

### Audit log coverage — pass
Spot-checked five sensitive mutation types named in CLAUDE.md rule 9 (stock-adjustment approval, B2B credit override, payment allocation, role/permission change, B2B price-override/discount) — every one has a real `recordAudit`/`audit()` call site, cited above in the relevant sections.

## Fixes applied in this pass

1. **Webhook rate limiting** (`apps/api/src/config/app-config.ts`, `apps/api/src/http/middleware/rate-limit.ts`, `apps/api/src/http/routes/checkout.routes.ts`, `apps/api/src/http/app.ts`): added a dedicated `webhook` rate-limit rule (120 requests/min per IP, defense-in-depth only — every request still needs a valid HMAC signature regardless of rate) and wired it onto `POST /api/store/payments/webhooks/:provider`, matching every other write endpoint on the same router. Test: `apps/api/src/http/checkout.routes.test.ts` — "rate-limits the unauthenticated webhook route per IP."

2. **Refresh-failure audit coverage** (`apps/api/src/modules/auth/auth.service.ts`): `refresh()` previously only audited the token-reuse-detected case; a malformed token, an unknown/already-revoked session, an expired session, a non-reuse secret mismatch, or a deactivated user all failed silently with no audit trail. Added a `reject(reason, actorId?)` helper that audits `AUDIT_ACTIONS.TOKEN_REFRESH_REJECTED` (previously-defined but dead code) with the specific reason before every rejection path, except the benign compare-and-swap race (two of the *same* caller's own concurrent refresh calls) which isn't a security event. Tests: `apps/api/src/http/auth.routes.test.ts` — "audits a rejected refresh even when it isn't token reuse" (covers `malformed_token` and `session_not_found_or_revoked`), plus an added assertion on the existing reuse-detection test confirming `SESSION_REUSE_DETECTED` is still recorded exactly once.

Both fixes are additive (a new rate-limit rule, additional audit calls on already-failing paths) — no existing behavior changed, no new dependency introduced, and the full 1618-test suite (up from 1616) plus `pnpm -r typecheck` are clean.

## What wasn't touched, and why

- **The two remaining Low findings** (per-account brute-force backstop; dead `SALES_DISCOUNT`/`SALES_OVERRIDE_PRICE` permissions) have no minimal, low-risk fix available without either inventing new infrastructure (a distributed brute-force detector) or a new route to enforce a currently-unused permission against (which would be adding functionality, not fixing a defect). Both are documented above with the reasoning, so they're tracked rather than silently dropped.
- **This audit did not attempt a live penetration test** (no traffic-generation or browser tool was available) — every verdict above is a source-code trace of the actual request path, cross-referenced against the existing automated test suite where one exists. That test suite is extensive and, on inspection, already proves each of the six specifically-requested scenarios; this pass's main value was independently verifying those tests actually assert what their names claim, not just adding more of the same coverage.

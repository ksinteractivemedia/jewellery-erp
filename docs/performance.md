# Performance Audit

Status: **complete** (2026-09-24). A pass across MongoDB query patterns, N+1s, aggregation pipelines, API payloads, React rendering, TanStack Query caching, images, bundle size, and code splitting — prioritized on ERP tables, inventory, reports, product listing, B2B catalogue, and the dashboard, per the task's own priority order.

**Method.** Two focused research tracks (backend/MongoDB; frontend rendering & data-fetching) read the actual implementation — models, services, aggregation pipelines, query hooks, components — and reasoned from the real query/render shape rather than guessing at cost. Where a number could be measured directly this session, it was: every `next build` in this document is a real, just-run build (not an estimate), and every fix below was verified against the existing test suite rather than assumed correct. No browser/profiling tool was available, so React re-render counts and actual page-load timings are reasoned from code (props stability, memoization, query configuration), not measured live — that limitation is called out wherever it matters, consistent with the same disclosure in `docs/ux-audit.md` and `docs/security-audit.md`.

**Headline result.** No area required a rewrite. The codebase's discipline holds up well in the areas it was clearly designed around (server-side pagination, denormalized reads instead of `.populate()`, indexed dashboard/gold-report aggregations) — the real findings cluster in a handful of specific places: one genuinely unindexed, full-scan endpoint (B2B catalogue), one real N+1 (B2B credit-utilization report), a few TanStack Query configuration gaps, and image optimization being entirely unused across both commerce-facing apps. Five backend fixes and six frontend fixes were made in this pass; the largest remaining item (converting several sales/profitability reports from Node-side reduction to real `$group` aggregations) is documented with full reasoning for why it wasn't attempted in this pass rather than risked half-verified.

## MongoDB — indexes, N+1, payloads, pagination, aggregations

### Fixed

1. **B2B wholesale catalogue was an unindexed full collection scan on every browse, search, filter, or sort — the worst-scaling endpoint found in this audit.** `apps/api/src/modules/b2b/b2b-reads.service.ts`'s `catalogue()` ran `ProductModel.find({isActive:true, b2bEnabled:true})` with **no supporting index** — `product.model.ts` indexed `{categoryId,isActive}`, `metalId`, `tags`, `updatedAt`, but never the `{isActive, b2bEnabled}` pair this query actually filters on, so every request scanned the entire `Product` collection regardless of the page/filter requested. It also fetched full `Product`/`ProductVariant` documents with no projection, pulling `description`/`videos`/`stoneDetails`/every image for every SKU × size variant on every request.
   *Fix:* added `productSchema.index({b2bEnabled:1, isActive:1})`, and added `.select(...)` to both queries listing only the fields `catalogueItem()`/`priceFor()` actually read (traced by reading both functions field-by-field, not guessed). Per-customer pricing/faceted search still runs in Node — see "documented, not fixed" below for why a deeper rewrite wasn't attempted. Verified: all 106 `b2b.routes.test.ts` tests pass unchanged, including the "wholesale catalogue" describe block's search/filter/sort/pagination/facet assertions.

2. **The B2B credit-utilization report was a real N+1: 3×N queries for N customers instead of 3 total.** `apps/api/src/modules/reports/b2b-reports.service.ts`'s `b2bCreditUtilization` looped every B2B customer calling `creditFor()` — which itself does 3 sequential queries (open invoices, paid-by-invoice aggregation, live orders) — one customer at a time via `Promise.all(customers.map(async c => ...))`. For a business with, say, 200 wholesale accounts, that's 600 round trips to load one report screen.
   *Fix:* added `creditPositionsFor()` (`apps/api/src/modules/b2b/b2b-core.ts`) — the same credit math (`creditPosition()`, already a pure function with zero I/O) fed by 3 **batched** `$in` queries across every requested customer at once, then grouped in Node. `creditFor()` itself is untouched and still used everywhere a single customer's position is needed (checkout, the portal's own credit panel) — this is a new, additive function for the one place that genuinely needs every customer at once. Also added `{customerId:1, status:1}` compound indexes on both `Invoice` and `SalesOrder` (the latter had **no indexes at all** beyond single-field ones on `customerId`/`status` separately), covering both the batched `$in` query and `creditFor()`'s own single-customer query. Verified: all 40 `reports.routes.test.ts` tests plus all 106 `b2b.routes.test.ts` tests pass unchanged.

3. **Inventory list table had no index for common filter+sort combinations.** `apps/api/src/modules/inventory/inventory-query.service.ts`'s `list()` lets a caller sort by any of `updatedAt|createdAt|itemCode|grossWeight|netWeight|fineWeight|cost|status` while filtering by `status`/`locationId`/`metalId`/etc. — but no index covered `status` (the single most common filter — "show me AVAILABLE stock") combined with `cost`, `itemCode`, or even the *default* `updatedAt` sort. A status-filtered, cost- or itemCode-sorted view of a large inventory would fall back to an in-memory sort over the whole filtered set.
   *Fix:* added `{status:1, updatedAt:-1}` (covers the default view — every unsorted inventory-list page load), `{status:1, cost:-1}`, and `{status:1, itemCode:1}` to `InventoryItemModel`. Deliberately not one index per possible sort field (7 sort fields × several filter fields would be real index bloat for combinations with no evidence anyone uses them) — these three cover the default view plus the two combinations actually named as risky.

### Documented, not fixed

4. **Most of the reporting module's "28 aggregations" are not aggregations — several do `Model.find()` + hand-rolled `Map` reduction in Node instead of MongoDB `$group`.** Counting `.aggregate()` vs `.find()` calls per report service file: `sales-reports.service.ts` is 0 aggregate / 18 find, `profitability-reports.service.ts` 0/2, `b2b-reports.service.ts` 0/3 (before fix #2 above). The worst two: `b2cDayTotals`/`b2bDayTotals` (`sales-reports.service.ts`) back **four** registry entries — `sales-daily`, `sales-monthly`, `sales-b2c`, `sales-b2b`, the first tab most users open in Reports — and pull every matching `Order`/`Invoice` document for the requested date range (up to the allowed 366 days) into the API process to reduce by hand, where `gold-reports.service.ts` and `inventory-reports.service.ts` already prove the better pattern exists in this same codebase (`$match` on an indexed field, `$lookup`, `$group`, `$facet` for pagination — correctly ordered, `$match` first).
   *Why not fixed here:* converting these functions changes the actual computation, not just its query plan — a real risk of a subtly wrong number in a financial report if rushed. The existing 40-test `reports.routes.test.ts` suite is a strong safety net for this (real fixtures, real assertions on summed totals), but a correct conversion of 4+ report functions from Node-reduction to `$group` deserves its own focused pass with that full suite as the verification loop, not a rider on a broader audit. **Recommended next step:** convert `b2cDayTotals`/`b2bDayTotals` first (highest traffic, and `OrderModel`/`InvoiceModel` already carry the exact indexes — `{status,placedAt}`, `{status,issueDate}` — the `$match` stage needs), using `gold-reports.service.ts`'s `$lookup`+`$facet` pattern as the template; `sales-by-product`/`sales-by-category`'s embedded-array unwinding is the next candidate after that.

5. **The B2B catalogue's filter/sort/facet computation still runs in Node on the full in-scope set, not pushed into MongoDB.** After fix #1, the base *fetch* is indexed and projected, but `catalogue()` still filters by search term/category/metal/purity/availability, sorts, and computes category/metal/purity facet counts entirely in Node before slicing the requested page — cost scales with total catalogue size, not page size.
   *Why not fixed here:* per-customer price (the sort key for `price-asc`/`price-desc`) comes from the pricing engine (customer/group/price-list rules), which cannot be computed inside a MongoDB query — pricing has to happen in Node regardless. Correct faceted-search counts (the category/metal/purity counts shown next to each filter option) also need the *search-filtered* set before category/metal/purity narrowing, which is a legitimate reason the current code materializes an intermediate array rather than a design oversight. A real fix would push the category-tree/metal/purity/availability filtering into the initial Mongo query (leaving only price-dependent sorting and pricing itself in Node, on a much smaller, already-filtered set) — a genuine improvement, but a bigger, correctness-sensitive rewrite of working search/facet logic that deserves dedicated test coverage of its own rather than being folded in here. The index + projection fix (#1) already removes the dominant cost (an actual collection scan); this is the next layer once that's proven out in practice.

### Verified correct, not touched

- **Indexes** for the priority modules' actual query shapes are otherwise well-matched: `InventoryItemModel`'s existing `{status,locationId}`/`{locationId,status,metalId}`/`{metalId,purity}` line up with `inventory-query.service.ts`'s real filter combinations; `InventoryLedgerModel`'s `{itemId,sequence}`/`{itemId,createdAt}`/`{movementType,createdAt}`/location indexes line up exactly with the gold reports' and dashboard's ledger queries; `OrderModel.index({status,placedAt})` matches every sales/profitability report's own `$match` shape.
- **No `.populate()` anywhere** in `apps/api/src/modules` (grep-confirmed) — the codebase consistently denormalizes/batches instead, as CLAUDE.md's data-model rules require.
- **N+1s are the exception, not the rule** — `inventory-query.service.ts`'s `itemContext()`, `inventory-reports.service.ts`, and `gold-reports.service.ts` all batch location/metal/product/variant name-resolution via `$in` for a whole page of rows at once; only the credit-utilization report (fixed above) and two harmless, bounded loops (a ≤6-word search in `product.service.ts`, a ≤6-line journal-entry loop in `posting.service.ts` — neither scales with collection size) do per-row queries.
- **Pagination is correct server-side `skip`/`limit` (or `$facet`) for every priority-module list endpoint** — inventory list, catalog admin product list, all report list-style endpoints, reports' CSV export (capped at a real, documented 10,000 rows, never silent truncation). The reports module's two pagination styles (`paginateArray` for output that's inherently small — grouped by day/status — vs. `facetPage` for output that scales with documents) are each individually correct; the inconsistency worth noting is that `paginateArray`'s justification is about *output* size, while the *input* fetched before grouping (finding #4 above) isn't bounded the same way — a reason to fix #4, not a bug in the pagination logic itself.
- **Well-ordered aggregations, cited as the pattern to follow:** `gold-reports.service.ts`'s `goldLedgerMovement` (`$match` on indexed `movementType`+`createdAt` → `$lookup` → `$unwind` → post-join `$match` → `$sort` → `$facet{data,count,totalFine}`) and `inventory-reports.service.ts`'s `inventoryReserved`/`inventoryDeadStock` (indexed `$match` → `$sort` → `$facet` with real `$skip`/`$limit`) both put `$match` first on indexed fields before the expensive stages — exactly right.
- **Dashboard aggregations** (`inventory-dashboard.ts`, `operations-dashboard.ts`) scale with distinct-group cardinality (metal×purity×location, or status), not document count — fine as inventory grows. No live `SalesProvider` is registered in production yet (dashboard sales section reports `NOT_CONNECTED`), so there's no sales-dashboard query to assess.

## Frontend — React rendering, TanStack Query, images, bundles, code splitting

### Fixed

6. **B2B portal had no default `staleTime` at all (TanStack's default is 0) — every order/invoice/PO/payment list refetched on every mount and every window/tab focus.** Unlike ERP (`staleTime: 30_000`) and B2C (same, with `refetchOnWindowFocus` left on), `apps/b2b-portal/components/providers.tsx`'s `QueryClient` set no default, so every hook in `lib/queries.ts` without its own override — purchase orders, quotations, orders, invoices, payments, returns — refetched constantly on exactly the screens a buyer revisits most while assembling a purchase.
   *Fix:* added `staleTime: 30_000` to the default `QueryClient` config, matching the other two apps' baseline. `refetchOnWindowFocus` stays on (reasonable for order/invoice freshness) — the fix means it won't refetch more than once per 30s even under rapid focus changes, rather than on every single one.

7. **`next/dynamic` was never used anywhere in the monorepo; the ERP's `CommandPalette` (`cmdk` + a Radix Dialog) was statically bundled into every page via `AppShell`, which wraps the entire ERP.** Most users never press ⌘K or open search on a given visit, so this weight (and its parse/execution cost) was paid unconditionally on every ERP page load.
   *Fix:* `apps/erp/components/app-shell.tsx` now dynamically imports `CommandPalette` (`next/dynamic(..., {ssr:false})`) and only mounts it the first time it's actually requested open (⌘K or the search icon) — the keyboard listener itself lives in `AppShell` independent of whether the palette component is mounted, so the shortcut still works identically; the chunk just isn't fetched/parsed until first use, and stays mounted (not torn down) after that so reopening doesn't re-fetch. **Measurement note:** this genuinely removes `cmdk`/Radix Dialog from the synchronous per-page import graph (verified by reading the resulting bundle — the component is no longer statically imported anywhere in the ERP app), which is the correct code-splitting outcome; the aggregate "First Load JS" numbers `next build` reports didn't show a clean, isolable delta for this specific change across two full production builds (too much page-to-page and build-to-build variance to attribute a precise KB figure to one change) — reported honestly rather than inventing a number.

8. **Nine status-filtered "tab" list queries lacked `placeholderData: keepPreviousData`, so clicking a status tab replaced the table with a full loading skeleton every time** — the exact "loading-state flash" pattern the reports/product-list/inventory screens already correctly avoid for *page-number* pagination, just not for *status-tab* filtering. Fixed on: `usePurchaseOrders`/`useRequisitions` (purchasing), `useB2BPurchaseOrders`, `useProductionOrders`/`useJobWorkOrders` (manufacturing), `useHallmarkingBatches`, `useExchanges`, `useReturns`, `useRepairOrders` — every status-parameterized list hook found across the ERP's workflow modules.

9. **Five reference-data hooks (categories, collections, suppliers, assaying centres, chart of accounts) had no `staleTime`, unlike their sibling `*Meta` hooks in the same files, which correctly use 5 minutes.** `useCatalogMeta`/`useInventoryMeta`/`usePricingMeta` all set `staleTime: 5*60_000`; `useCategories`/`useCollections` (`lib/api/queries.ts`), `useSuppliers` (`lib/api/purchasing.ts`), `useAssayingCentres` (`lib/api/hallmarking.ts`), and `useChartOfAccounts` (`lib/api/accounting.ts`) did not, so genuinely slow-changing reference lists refetched on every 30-second staleness window like live transactional data.
   *Fix:* added `staleTime: 5*60_000` to all five, matching the established sibling convention.

### Measured directly (not estimated)

10. **Real bundle sizes**, from an actual `next build` of each app (all three are healthy for a Next.js 14 app; none is alarming, but the relative shape is worth recording as a baseline for future comparison):
    - **ERP**: shared baseline ~87.6–87.8kB; heaviest routes are `/inventory/products/new` (~235kB), `/inventory/stock/new` (~224kB), `/inventory/stock` (~216kB), `/` dashboard (~194kB) — all form-heavy or chart-heavy screens, consistent with their actual content rather than a bloat symptom.
    - **B2C**: shared baseline ~87.3kB; heaviest is `/product/[slug]` (~217kB, gallery + purchase panel + live pricing) and the home page (~211kB). Notably, B2C's home page is server-rendered **on demand** (`ƒ`), not statically generated (`○`) — see finding #12 below.
    - **B2B portal**: shared baseline ~87.3kB; every route is a lean 119–123kB — the leanest of the three apps by a wide margin, a direct consequence of the portal's own local `.btn`/`.field` CSS system instead of `packages/ui`'s richer component set (already flagged architecturally in `docs/ux-audit.md`'s B2B findings — smaller bundles are the one real upside of that otherwise-not-recommended pattern, noted here for completeness, not as a reason to keep it).

11. **`next/image` is used nowhere in this codebase — confirmed by grep across all three apps and `packages/ui`, zero hits.** Every product image, gallery image, cart thumbnail, and catalogue row image is a raw `<img>`. This is deliberate, not an oversight: `apps/b2c-store/components/ui/progressive-image.tsx` is a real, working custom component (tinted placeholder, blur-up fade transition, monogram fallback on failure, correct `loading="lazy"`/`priority` usage — verified `priority` is only set on the hero, first gallery image, and first 4 grid items, everything else genuinely lazy) with an explicit `eslint-disable @next/next/no-img-element` acknowledging the departure.
    **The real bug, not just "next/image would be nicer":** `ProgressiveImage` accepts and forwards a `sizes` prop (`product-card.tsx` passes `sizes="(min-width:1024px) 25vw, 50vw"`) onto a plain `<img>` with only a single `src` and **no `srcset`** — the `sizes` attribute does nothing without a corresponding `srcset`, so every product thumbnail ships the same full-resolution file to a phone in a 2-up grid as to a desktop hero. B2B's catalogue table (`app/(portal)/catalogue/page.tsx`) has the same root cause for its 40×40px row thumbnails. Compounding this: `apps/api`'s media service (`apps/api/src/modules/media/`) has **no resizing capability at all** — no `sharp`, no width/quality params — so there isn't even a server-side variant to reference; the original uploaded file is what's served, at every size, everywhere.
    *Why not fixed here:* a real fix (routing images through `next/image`, or adding resize-on-upload/on-request to the media service) touches ~12 call sites across two apps and a shared UI library, changes real visual behavior (loading transitions, layout), and — critically — this session has no browser to visually verify the result renders correctly. `next.config.js` in both `apps/b2c-store` and `apps/b2b-portal` has no `images` block at all, and the media origin (`API_PUBLIC_URL`) is only known at runtime via env var — solvable (Next's own image proxy works with any origin once `remotePatterns` is configured, and `next.config.js` can read `process.env` at build/start time), but real configuration work, not a one-line fix. **This is the single highest-impact unaddressed finding in this audit** — B2C is the highest-traffic, most image-dense app in the monorepo, and every visit currently pays for full-resolution images regardless of how small they render. Recommended next step: add resize-on-upload to the media service (even a fixed set of 2–3 width variants at upload time, written alongside the original, would let a real `srcset` be built without needing `next/image`'s live proxy at all) — that's the piece both a `next/image` migration and a hand-rolled responsive-image fix would both need, so it's the right place to start regardless of which direction is chosen later.

12. **B2C's home page renders dynamically (`ƒ`) on every request rather than being static or ISR-cached, unlike most of its other routes.** Confirmed via the `next build` route table. Given the storefront's own architecture already solves the "no blank flash" problem for listing pages via server-fetched `initialData` handed to a client `useProducts` call (`apps/b2c-store/components/listing/listing-view.tsx`), the home page not being static is likely because it embeds live pricing (`PriceTag`, metal-rate-dependent) that genuinely can't be static — reasoned through, not assumed, and not flagged as a defect: static generation would either show a stale price or require the same live-price fetch client-side anyway, so `ƒ` is the honest choice here, not a missed optimization.

### Documented, not fixed

13. **`packages/ui/src/components/data-table.tsx` (the shared table every ERP list screen uses) does no memoization — zero `React.memo` usage anywhere in `apps/` or `packages/ui/src`, and only 3 uses of `useMemo` in all of `apps/erp/components`.** `apps/erp/components/catalog/product-list.tsx` reproduces the textbook case: its `columns` array is rebuilt with fresh closures on every render, and a debounced search box's local state re-renders the whole list component (and therefore reconstructs `columns`) on every keystroke, with no memoization anywhere in the chain to short-circuit it.
    *Why not fixed here:* every one of these screens is already server-paginated to 25–100 rows (verified — see the pagination section above), which is precisely what keeps the actual cost of a full re-render bounded today; the frontend research track rated this "Medium impact, bounded by pagination" for exactly that reason, not "currently slow." Wrapping `DataTable` in `React.memo` and the various `columns` arrays in `useMemo` is genuinely safe (pure performance, no behavior change) and would be the natural next increment, but doing it correctly across every list screen that uses the pattern is a wide, mechanical change better done as its own pass with the resulting render count actually profiled (which needs a browser) rather than bundled here on faith that it's an improvement everywhere it's applied.
14. **No ERP route ever prefetches on the server via TanStack Query's `dehydrate`/`HydrationBoundary`** (grep-confirmed, zero hits repo-wide) — every first paint of the dashboard or the reports registry is a guaranteed blank-skeleton-then-populate sequence, even on a warm cache, since nothing seeds the query cache before the client mounts. B2C already proves this pattern works in this exact codebase for its listing pages (`initialData` handed from a Server Component fetch). *Why not fixed here:* introducing server-side prefetching to the ERP dashboard/reports pages is a real architectural change to how those specific pages are composed (a new Server Component data-fetch layer that doesn't exist there today), and doing it for two screens without establishing the pattern deliberately (and verifying the hydration boundary actually eliminates the flash, which again needs a browser) risks a half-adopted pattern rather than a real fix. Flagged as the natural pairing with finding #7's `dynamic()` work — both are "make the first paint honest" fixes — for a follow-up that can carry a browser check.

## What's next

In rough impact order: **image resizing at the media service** (finding #11 — the prerequisite for any real image-optimization work, and the single biggest unaddressed cost given B2C's traffic), **sales/profitability report aggregation conversion** (finding #4 — the biggest remaining backend win, gated on dedicating real verification time to a financial-report change), **B2B catalogue facet/filter push-down** (finding #5 — the deeper fix behind today's index/projection patch), and **`DataTable` memoization + ERP dashboard/reports SSR prefetch** (findings #13/#14 — both genuinely safe, both better done with a browser in the loop to confirm the visible improvement rather than taken on faith).

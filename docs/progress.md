## Phase 10 — Reporting (2026-09-23)

**Status: 28 reports across Sales, Inventory, Gold, B2B and Profitability, all served through one registry-driven framework — one dispatcher, one filter contract, one generic ERP screen — rather than bespoke screens per report.** No new persisted collections: every report reads existing data through a backend MongoDB aggregation (or, for the handful already exposed by Accounting/B2B, a thin paginated wrapper over that module's own tested reads).

Produced:
- **`packages/types/src/reports.ts`** — `REPORT_CATEGORIES`, `REPORT_KEYS` (28), `ReportFilterKind`, `ReportColumn`/`ReportColumnFormat`, `ReportDefinition` (the registry row: title, description, which filters apply, columns, `snapshot`/`groupByOptions`), `ReportSummaryFigure`, `ReportResult`.
- **`apps/api/src/modules/reports`** (new module, no model of its own):
  - `report-registry.ts` — the 28 `ReportDefinition`s; adding a report is one registry row plus one function, never a new route or screen.
  - `report-filters.ts` — `resolveReportContext` (shared date-range/branch-location resolution, reusing the dashboard's own `resolveRange`/`resolveScope`, so a report and the dashboard treat a date/branch/location filter identically), `paginateArray` (in-memory, for reports whose row count is a group count) and `facetPage` (a real Mongo `$skip`/`$limit` inside the aggregation, for reports whose row count scales with documents).
  - `sales-reports.service.ts` / `inventory-reports.service.ts` / `gold-reports.service.ts` / `b2b-reports.service.ts` / `profitability-reports.service.ts` — the computations. Sales reports scoped to a branch/location honestly: `Order`/`Invoice` carry no location field, so scope is derived from the real `SALE` ledger entry's `sourceLocationId`, joined back through `Transaction` (an order fulfilled from more than one location is attributed whole to the first location sold from — a documented simplification, not an invented field). Gold's purchased/issued/consumed/sold/returned reports read the ledger via a shared `$lookup`-based pipeline joined to `InventoryItem` for metal/purity, using each entry's `balanceAfter.grossWeight`/`fineWeight` rather than the entry's own delta — a whole-piece movement never splits a batch (business-rules.md §15.3), so the ledger's own delta is 0 for a custody move that doesn't change the piece's weight, and `balanceAfter` is the piece's real weight at that event either way. Gold wastage isn't a ledger movement at all (business-rules.md §15.5 — it's a `reconciliation.wastageGrossWeight` field on a closed `ProductionOrder`/`JobWorkOrder`), so that report reads Manufacturing's own data directly instead. B2B outstanding/ageing are thin paginated wrappers over Accounting's own `receivables-reads.service.ts` — never re-derived; customer-sales/credit-utilization/PO-pipeline are new aggregations. Profitability re-derives COGS from `InventoryItem.cost` via the `SALE` ledger (channel-agnostic, since an item's cost doesn't care who bought it) rather than reading `AccountingEntry`, since GL posting is B2B-only so far (Phase 9) and a profitability report can't silently omit B2C.
  - `reports.service.ts` — `RUNNERS` dispatch table + `runReport` (resolves context once, dispatches, then stamps the registry's own key/title/columns onto the result — a report function never needs to know its own display metadata); `runReportForExport` reuses the same paginated function with `pageSize` overridden to a fixed `EXPORT_MAX_ROWS = 10_000` rather than the page size the screen is showing.
  - `csv.ts` — CSV export with proper cell escaping.
- **Routes** (`GET /api/reports/registry`, `GET /api/reports/:key`, `GET /api/reports/:key/export`), behind the existing `reports.view` permission (no new permission needed) — the export route sets `Content-Disposition: attachment` and streams a capped CSV instead of the browser ever holding the full result as JSON.
- **Indexes added on existing, already-tested models**, matched to the reporting module's own query patterns: `Order` on `{status, placedAt}`; B2B `Invoice` on `{customerId, dueDate}` and `{status, issueDate}`; B2B `PurchaseOrder` on `{status, createdAt}`.
- **ERP screens** (`apps/erp/components/reports`, `Reports` nav entry now owning its own header): `ReportIndexView` — the registry, grouped by category, as link cards (nothing hand-maintained: a new registry entry appears here for free). `ReportView` — one generic screen for all 28 reports: a filter bar built from the report's own declared `filters` (date range, branch, location, customer type, category, group-by — each control only rendered when the report actually uses it), summary tiles, `DataTable` with columns/formatting driven entirely by the registry's `ReportColumn`s (money/weight/percent/number/date — the browser formats, never computes), pagination, and a CSV export button that downloads through an authenticated `fetch`+blob (the same private-file pattern already used for B2B PO attachments, never a bare link, since the access token lives only in SPA memory per CLAUDE.md rule 10).

**Verified, not claimed:** `pnpm -r typecheck`, `pnpm -F @jewellery/erp lint`, and production builds of all Next.js apps are clean. **1616 API tests passing** (+40 this phase, `reports.routes.test.ts`) covering: authorization (all 13 roles × `reports.view`), the registry, filter validation (bad dates, an out-of-branch location, an oversized range, an unknown report key), and real correctness for every category — daily/monthly/B2C/B2B/by-product/by-category/by-salesperson/by-branch sales built from real sold `Order`s and issued B2B `Invoice`s; all 7 inventory reports against real `InventoryItem`s (including a dead-stock cutoff and a reserved item); all 7 gold reports including a full return flow (sale → request → approve → receive) and a full production-order flow taken through issue-material → start → submit-QC → pass → complete to prove issued/consumed/wastage; all 5 B2B reports including a real overdue invoice and a real PO; profitability's revenue/cost/margin arithmetic against a known item cost; pagination; and CSV escaping. Writing this test suite caught one real bug fixed as part of this phase: `goldLedgerMovement` was reading each ledger entry's own `grossWeight`/`fineWeight` delta fields, which are 0 for any whole-piece custody move (issue, sale, return) that doesn't change the piece's physical weight — fixed to read `balanceAfter` instead, as described above. Not run against a live browser (no Playwright/browser-automation tool was available this session) — screens are typechecked, linted and production-built, matching the same disclosed limitation as Phase 9.

Not done, deliberately: no new collection or persisted "saved report"/scheduling — every figure is computed live, per the task's "use backend aggregation pipelines" instruction; profitability is one report with `groupBy` (day/month) rather than five separate ones, since its five bullets (revenue/cost/gross profit/margin/discounts) read as columns of one P&L view rather than five distinct grouping dimensions — a deliberate interpretation, unconfirmed by the user; CSV export is capped at 10,000 rows rather than true unbounded streaming (protects the browser; a report already grouped/aggregated or itself a snapshot rarely approaches that cap).

## Phase 9 — Accounting: the first layer (2026-09-23)

**Status: a real double-entry general ledger — `ChartOfAccount` + `AccountingEntry`, posted by one shared abstraction — now sits under the ERP's existing B2B invoicing/payments and Procurement's supplier invoices/payments, with a Receivables Dashboard, Outstanding list, Ageing report and Credit/Debit notes in the ERP.** Deliberately not a full accounting package, per the task's own instruction: no multi-currency, no cost centres, no budgets, no manual free-form journal entries, no tax-filing reports.

Produced:
- **`ChartOfAccount`** (`apps/api/src/modules/accounting`): a real chart, seeded as policy-as-code (`syncChartOfAccounts`, upserted at every boot like `role-matrix.ts`'s system roles) covering Cash, Bank, Accounts Receivable, Inventory, GST Receivable, Accounts Payable, GST Payable, Owner's Equity, Sales Revenue, Discount Given, Purchases, Cost of Goods Sold. The posting engine never hardcodes an account id — it resolves "the AR account" by `systemRole`, and a unique partial index guarantees at most one active account holds a role at a time; deactivating the last holder of a role is refused. A business can freely rename, describe, deactivate, or add its own non-system accounts through the new Chart of Accounts screen.
- **`AccountingEntry`** — one balanced journal entry (a header + debit/credit lines) per posting, append-only exactly like `InventoryLedger`/`Transaction` (the same `appendOnlyPlugin`). `postJournal` (`posting.service.ts`) is **the transaction abstraction the task explicitly asked for**: it resolves each line's account by role, drops zero-amount lines, and refuses to write anything where debits and credits disagree — the one function every accounting posting in the system calls, whether it's a sale or a purchase.
- **Sales posting** (`sales-posting.ts`), wired into `b2b/fulfilment.service.ts`'s `invoice()` inside its existing ledger transaction: Dr Accounts Receivable (what's owed), Dr Discount Given (any concession, its own line — never netted invisibly into revenue), Cr Sales (the *gross*, pre-discount amount), Cr GST Payable — and, because every `InventoryItem` already carries its own book cost, Dr Cost of Goods Sold / Cr Inventory at the sold pieces' *actual* cost (a real perpetual-inventory posting, not an estimate). `postPaymentReceived`, wired into `payments.service.ts`'s `allocate()`, posts Dr Cash or Bank (by payment method) / Cr AR for exactly the amount applied in that call; `reverse()` posts the exact opposite via a new `reverseJournal` entry, never an edit.
- **Purchase posting** (`purchase-posting.ts`), wired into `procurement/supplier-invoice.service.ts`'s `createSupplierInvoice()` — the liability is booked at the bill, not the earlier goods receipt, since goods may arrive before their invoice does: Dr Inventory for ledger-tracked lines (the ones that become a real `InventoryItem` — reusing procurement's own existing `isLedgerTracked` split, not re-decided here), Dr Purchases for `CONSUMABLE` lines (which never become stock), Dr GST Receivable (input credit), Cr Accounts Payable. Cancelling an (unpaid-only) supplier invoice reverses its posting. `postPaymentMade`, wired into `supplier-payment.service.ts`'s `allocateSupplierPayment()`/`reverseSupplierPayment()`, is the AP-side mirror of the payment-received posting.
- **`CreditNote`/`DebitNote`** — new, standalone documents. A credit note (`SALES_RETURN | PRICE_ADJUSTMENT | GOODWILL | OTHER`) always reduces AR (Dr Sales + GST Payable, Cr AR); a debit note (`PURCHASE_RETURN | PRICE_ADJUSTMENT | SHORT_SUPPLY | OTHER`) always reduces AP (Dr AP, Cr Inventory + GST Receivable). Either may be cancelled, which posts the exact reversal. Not (yet) auto-issued from a B2B Return's settlement — a natural follow-up, deliberately not built this phase (see below).
- **`Payment`/`PaymentAllocation` — deliberately not new collections.** B2B's `B2BPayment`/`PaymentAllocation` and Procurement's `SupplierPayment`/`SupplierPaymentAllocation` (Phases 4 and 5) already implement exactly this, fully tested, per channel; reimplementing them a third time would be the "recreate Tally" the task explicitly warned against. Allocating or reversing either now *also* posts a GL entry, through the one shared function, in the same database transaction as the allocation itself.
- **Receivables Dashboard, Outstanding, Ageing** (`receivables-reads.service.ts`, new `/api/accounting/receivables/*`): total outstanding, total overdue, ageing buckets (current / 1–30 / 31–60 / 61–90 / 90+), and every open invoice — across *every* B2B customer, the accounts team's own view (distinct from the portal's per-customer outstanding page). Reuses B2B's own `ageInvoices`/`isOverdue`/`daysOverdue`/`invoiceStatus`/`paidByInvoice` rather than re-implementing ageing math a second time. Payment allocation itself is **not** duplicated as a new screen — the Receivables Dashboard links straight to the B2B desk's existing, fully-built Invoices & Payments screen (Phase 4b).
- **Trial balance** (`reports.service.ts`) — a proof, not just a report: since `postJournal` never writes an unbalanced entry, summing every posted debit and credit by account should always foot to the same total on both sides.
- **New permission** `accounting.manage` (Chart of Accounts writes, credit/debit note issuance/cancellation), held by `ACCOUNTANT` alongside the existing `accounting.view`/`accounting.create_payment`; every sensitive step audited.
- **ERP screens** (`apps/erp/components/accounting`, a new **Accounting** nav group replacing the old placeholder entry): Receivables (dashboard + ageing + outstanding table), General Ledger (filterable journal + trial balance), Chart of Accounts, Credit Notes, Debit Notes.

**Verified, not claimed:** `pnpm -r typecheck`, `pnpm -r lint` and production builds of all Next.js apps are clean; **1576 API tests passing** (+15 this phase — deliberately **not** a separate logic-only suite, since the posting engine has no state machine of its own to test in isolation; instead appended directly to `b2b.routes.test.ts` and `purchasing.routes.test.ts` as `describe("accounting: …")` blocks, so a change to the real invoicing/payment flow and a change to its accounting entry are proven together). Every existing B2B/Purchasing test still passes unmodified — the two test files needed only a `seedChartOfAccounts()` call added to their `beforeEach`, the same way they already call `seedRbac()`.

Not done, deliberately: **B2C sale posting** (the task's own detailed workflow is B2B: "Invoice → Outstanding → Payment → Allocation → Outstanding reduced" — `postSalesInvoice` is channel-generic and ready, but nothing calls it from checkout capture yet); **auto-issuing a CreditNote when a B2B Return is settled** (Returns, Phase 8, already has a `settlement.method` — wiring it to `createCreditNote` is a natural follow-up, not done to keep this phase's scope to what was asked); **a free-form manual journal entry** (every posting traces to a real commercial document by design, not an oversight); **multiple cash/bank accounts** (one Cash role, one Bank role — a business with several bank accounts needs a future enhancement); **GST input-credit netting against output liability** (GST Payable and GST Receivable are both tracked and both show in the trial balance, but nothing nets one against the other into a single payable/refund figure — a GST return itself is out of scope); Playwright browser checks (screens are typechecked, linted and production-built, not run against a live browser).

## Phase 8 — Returns, Exchange & Repair (2026-09-23)

**Status: B2C and B2B Returns, old-for-new Exchange, and end-to-end Jewellery Repair all work in the ERP, with real customer-facing status/request in the B2C storefront and the B2B portal — on the same explicit-state-machine, ledger-only-movement discipline as every workflow module before it (Phases 4b–7).**

Produced:
- **Returns** (`apps/api/src/modules/returns`): `REQUESTED → APPROVED/REJECTED → RECEIVED → INSPECTED → SETTLED`, or `CANCELLED` before the piece is physically back (`returns-status.ts`). A return always identifies the **exact `InventoryItem`** an order actually sold — `order-context.ts` resolves this from the order's/sales order's own `allocations` (never trusted from the request), and validates original order, item, customer (scoped by order-access-token for a B2C guest, by database-resolved customer id for a B2B buyer — never client-supplied), HUID (a mismatch at receipt refuses outright) and weight (a drift needs a note) — the six things the spec named. Receipt posts the existing `RETURN` ledger movement `SOLD → RETURNED`; inspection posts `RETURNED → AVAILABLE`/`DAMAGED` per piece. Settlement (refund/store credit/invoice adjustment) is a financial record with no further stock movement. `Product.quantity` does not exist and is never touched.
- **Exchange** (`apps/api/src/modules/exchange`): old jewellery → inspection → weight/purity assessment → valuation → new product → difference payable/refundable, `DRAFT → ASSESSED → COMPLETED`/`CANCELLED`, staff-only at the counter. The old piece is weighed and valued on the business's own scale/purity table (never on what's claimed), using the **same** `valueOfMetal` formula the pricing engine and stock valuation already use (CLAUDE.md rule 1) — `netWeight`/`fineWeight`/`valuation` are always server-computed, never accepted as input. Completing takes the old piece in as a real, ledgered `InventoryItem` (`EXCHANGE_IN`, the same creation discipline as a purchase receipt) and computes the settlement difference — positive (customer owes) or negative (business owes), never clamped.
- **Jewellery repair** (`apps/api/src/modules/repair`): Customer → repair intake → inspection → estimate → approval → repair → QC → ready → delivery/pickup (`repair-status.ts`), with `DECLINED`/`CANCELLED` both handing the piece straight back unrepaired and `QC_FAILED` looping to `IN_PROGRESS` for rework. Intake **is** the ledger movement (no separate "held for later" stage): against a piece already sold to this customer (`SOLD → UNDER_REPAIR`, extending the existing `REPAIR_OUT` movement to accept a `SOLD` origin) or, for a piece the business has never held (`isCustomerOwned`, new field), created fresh via a new `REPAIR_INTAKE` movement straight into `UNDER_REPAIR`. Before/after weight, stones, labour, materials and other charges are all tracked as real facts (`beforeWeight`/`afterWeight`/`estimate`/`finalCharges`), with the after-weight and final charges recorded *before* the QC decision. Leaving custody — decline, cancel, or deliver — is always a new movement type, `REPAIR_RETURN` (`UNDER_REPAIR → SOLD` for a piece that was already the customer's, or `UNDER_REPAIR → RETURNED_TO_CUSTOMER`, a new terminal status, for one the business never owned) — deliberately never `REPAIR_IN`, which stays reserved for the business's own pre-sale stock and would otherwise land a customer's piece on sellable `AVAILABLE` shelf stock.
- **New ledger vocabulary**, additive only: `InventoryStatus` gains `RETURNED_TO_CUSTOMER` (terminal); `MovementType` gains `EXCHANGE_IN`, `REPAIR_INTAKE`, `REPAIR_RETURN`; `InventoryItem` gains `isCustomerOwned`. All three new movements were added to `movement-rules.ts`/`status-transitions.ts` and proven, by the existing exhaustive movement-rules test, to still agree with the status graph.
- **New permissions**: `returns.view/create/approve`, `exchange.view/create`, `repair.view/create/approve` (QC is its own gate, mirroring `production.approve`), assigned to `STORE_MANAGER`, `SALES_MANAGER`, `SALES_EXECUTIVE` (view/create only), `INVENTORY_MANAGER` (view only), `B2B_MANAGER` and `CUSTOMER_SUPPORT` (view only) in the role matrix.
- **Customer-facing status and requests, for real** — not just an ERP-only workflow:
  - **B2C storefront**: the existing order page (`apps/b2c-store/app/orders/[orderNo]`) gained a Returns section — status of any existing return, and (once the order has actually been paid) a request form. A guest names their order's own **lines** (`lineRefs`), never an internal `InventoryItem` id they don't have — the server resolves the line → item mapping itself, the same "the backend recalculates everything" discipline every other checkout endpoint already follows. Guarded by the existing order-access-token, exactly like every other guest order action.
  - **B2B portal**: the sales-order detail page (`apps/b2b-portal/app/(portal)/orders/[id]`) gained the same Returns section, scoped by the buyer's own database-resolved customer id (`reads.salesOrder(id, {customerId})` is the ownership check — a request can never even name another customer's order).
  - Approval, receiving, inspection and settlement stay staff-only in both cases — the ERP's Returns screen.
- **ERP screens** (`apps/erp/components/{returns,exchange,repair}`, `apps/erp/app/(dashboard)/{sales/returns,sales/exchanges,repairs}`) — filled in the three placeholder nav entries the shell had carried since Phase 0.75 rather than adding new ones: a dashboard (status counts), a filterable list, and a detail panel driving every action, each screen using the design system's existing table/badge/form primitives. A small `SoldItemPicker` (status-filtered variant of hallmarking's `ItemPicker`) lets staff pick a return/repair-intake piece by item code or HUID.

**Verified, not claimed:** `pnpm -r typecheck`, `pnpm -r lint` (ERP, b2c-store, b2b-portal) and production builds of all three Next.js apps are clean; **1561 API tests passing**, **224 new this phase** (191 logic — exhaustive action×status matrices for all three new state machines — and 33 HTTP: full-flow tests with real ledger assertions for B2C and B2B returns, including the HUID-mismatch refusal, the weight-discrepancy note requirement, and the duplicate-open-return refusal; the exchange valuation cross-checked against a hand computation; the repair flow including the customer-owned-piece path, QC fail→rework, and cancellation from every working stage; a fourth small suite exercising the guest/buyer-scoped customer-facing endpoints specifically, proving a wrong order token and a request for another customer's order both fail closed). One pre-existing test (`movement-rules.test.ts`'s "only receipt-style movements can create stock") needed updating for the two new creation movement types — not a bug, an assertion that had to grow with the vocabulary.

Not done, deliberately: a **return that automatically triggers a real payment-gateway refund** (settlement is a financial record, like every other offline-money step in this codebase — B2B/procurement payments work the same way; wiring `REFUND` to the B2C payment provider's own `refund()` is a natural follow-up once returns see real traffic); an **order/item picker in the ERP's "new return" and "repair intake" forms** (staff enter the order's own id directly — the B2C/B2B ERP order-detail screens this would normally launch from don't exist yet either, per Phase 3.5/4's own gaps, so this is the same honest limitation, not a new one); a **return deadline/eligibility window** (a return can be requested against any order whose item is currently `SOLD`, with no time limit — the business rule for how long after delivery a return is allowed isn't specified yet, and DELIVERED-tracking itself isn't driven by anything in this system yet per Phase 3.5); Playwright browser checks (screens are typechecked, linted and production-built, not run against a live browser).

## Phase 7 — Hallmarking (2026-09-22)

**Status: Inventory Item → Send to Hallmarking → In Transit → At Hallmarking Centre → Received → Verified/Failed works end to end in the ERP — the same explicit-state-machine, ledger-only-movement discipline as B2B (Phase 4b), Purchasing (Phase 5) and Manufacturing (Phase 6).**

Produced:
- **Hallmarking batches** (`PENDING → IN_TRANSIT → AT_CENTRE → RECEIVED`, or `CANCELLED`) against an **assaying centre** — reference/configuration data (`AssayingCentre`, referencing a real `HALLMARKING_CENTER`-type location), never a hardcoded list, per the spec's "do not hardcode regulatory assumptions." Verified/Failed are deliberately **per-piece outcomes** once a batch is back, not batch statuses — one shipment can come back with some pieces verified and others failed at once; every screen shows a piece's *effective status* (its own outcome once it has one, otherwise its batch's shared stage), never a stored field.
- **Every physical movement is a real ledger entry**: dispatch posts `HALLMARKING_OUT` for every piece in the batch, in one transaction, to the centre's own location; receipt posts `HALLMARKING_IN`, back to each piece's *own* location — remembered at dispatch (`HallmarkingLine.fromLocationId`, the same pattern Phase 6 established) — never into the centre's location itself, which isn't a stock location.
- **A batch's receipt is all-or-nothing**: every piece on the batch must be accounted for in the one receive call (with a HUID, or without one if it came back unmarked/rejected) — refused otherwise, so a batch can never read `RECEIVED` while one of its pieces is still physically away.
- **The HUID is unique where applicable**, enforced by the one already-existing shared rule everywhere a HUID is ever set on an `InventoryItem` (`inventory-transaction.service.ts`) — not re-implemented here. Stored uppercase, so case differences collide as the same mark, and never changeable once set.
- **ERP screens**: a Hallmarking Dashboard (counts by Pending/In Transit/At Centre/Received/Verified/Failed, with the same tabs filtering the working batch list below — create-batch form with an item picker, and a batch detail panel driving dispatch/arrive/receive/verify/fail/cancel) and an Assaying Centres screen — one new **Hallmarking** nav group with two entries. The existing Inventory Item Detail screen's "Purity & hallmark" card gained a **Hallmarking History** section (every batch a piece has ever been part of, newest first) — HUID and Hallmark Status were already shown there from Phase 1.7.
- **Audit logs** on every sensitive step: dispatch, receipt, verify, fail, cancellation.

**Verified, not claimed:** `pnpm -F @jewellery/api typecheck`, `pnpm -F @jewellery/erp typecheck`, `pnpm -F @jewellery/erp lint` and `pnpm -F @jewellery/erp build` all clean; **+40 API tests** (26 state-machine/validation unit tests, 14 HTTP tests covering the full flow with real ledger and audit-log assertions, explicit HUID-uniqueness enforcement, and the item-history read the item-detail screen depends on). A real bug the tests caught before this note was written: `receiveHallmarkingBatch` accepted a receive call naming only *some* of a batch's pieces, moved just those through the ledger, but still flipped the whole batch to `RECEIVED` — leaving the omitted pieces stuck in `HALLMARKING` with no path back except a manual fix. Fixed by refusing any receive call that doesn't account for every piece on the batch.

Not done, deliberately: a **hallmarking-cost/fee tracking** (what the centre charges per piece isn't recorded — nothing in the spec asked for it, and it would duplicate Purchasing's supplier-invoice machinery for what is, structurally, a service purchase); a **due-date/overdue reminder** (`expectedReturnDate` is recorded and shown, nothing alerts on it yet — the same gap Phase 6 left on job-work due dates); Playwright browser checks (screens are typechecked, linted and production-built, not run against a live browser).

## Phase 6 — Manufacturing & job work (2026-09-22)

**Status: Production Order → Material Issue → Manufacturing → QC → Finished Jewellery → Inventory, and job work (issue to a vendor → return: finished goods, unused material, wastage, discrepancy), both work end to end in the ERP — on the same explicit-state-machine discipline as B2B (Phase 4b) and Purchasing (Phase 5), and wired directly into the same inventory ledger.**

Produced:
- **Production orders** (`DRAFT → MATERIAL_ISSUED → IN_PROGRESS → QC_PENDING → QC_PASSED/QC_FAILED → COMPLETED`, or `CANCELLED`; `QC_FAILED` can go back to `IN_PROGRESS` for rework) — a bill of materials fixed at creation (metal, purity, expected gross weight, expected wastage, stones required), actual weight/wastage/labour cost recorded at QC submission (before the decision, so the numbers the decision is made on are on the record), and a real QC gate: nothing completes without passing it.
- **Job work orders** (`DRAFT → ISSUED → PARTIALLY_RETURNED/RETURNED`, or `CANCELLED`) against a vendor (a `Supplier` — no separate vendor model), with issue/due dates, the same BOM shape, making charges, and **multiple return events** (a job worker can send back some finished pieces and some unused material now, more later) — the order only closes when a return is explicitly marked `final`, not inferred from weight-matching (a partial return legitimately hasn't accounted for everything yet).
- **Every physical movement is a real ledger entry, never a quantity edit**: material issue moves *whole* existing `InventoryItem`s (a batch is never split — splitting would incorrectly flip the un-issued remainder's status too, since it's the same document) via `MANUFACTURING_ISSUE`/`JOBWORK_ISSUE`; a finished piece is a brand-new `InventoryItem` created via `MANUFACTURING_RECEIPT`/`JOBWORK_RECEIPT` (tagged `manufacturingInfo.productionOrderId`/`jobWorkOrderId` — a field `InventoryItem` had declared since Phase 1.7 but nothing could set until now); unused material returns *whole*, back to the exact location it was issued from (never into the manufacturing unit or job-worker location itself, which aren't stock locations — each issued item remembers where it came from, `MaterialItemRef.fromLocationId`).
- **Material reconciliation**: issued − returned − finished − wastage = discrepancy. A discrepancy beyond a small, fixed tolerance (scale rounding, not a percentage) is refused unless a note explains it, and clearly flagged once one is given — the same discipline as Purchasing's goods-receipt weight check. Never silently absorbed into wastage; a negative discrepancy (more came back than went out) is shown as such, not clamped to zero.
- **A reconciliation screen**, as asked: ISSUED / RETURNED / FINISHED / WASTAGE / DISCREPANCY for every production order and job-work order that has had material issued, production and job work side by side (the material accounting is the same question either way), discrepant rows sorted first and highlighted, with a discrepancies-only filter.
- **ERP screens**: a Production Orders screen (create with a design/BOM/manufacturing-unit picker, an item picker for material issue, start/submit-for-QC/complete forms, cancel), a Job Work screen (vendor/BOM/job-worker-location picker, issue, a return form supporting partial-then-final returns), a Quality Control queue (pass/fail right from the list, no need to open the order), and the Reconciliation screen — four new nav entries under **Production**.

**Verified, not claimed:** `pnpm -r typecheck` and `pnpm -r lint` clean across all 9 workspaces; **+199 API tests** (92 state-machine/reconciliation-math/validation unit tests, 107 HTTP tests covering the full production and job-work flows, and explicitly the two requested categories — *material reconciliation* and *stock movement*); the full monorepo suite green (a 3-test flake seen in one run was the pre-existing, already-documented resource-contention issue in `b2b.routes.test.ts` — confirmed by re-running that file alone, clean). ## Phase 5 — Purchasing (2026-09-22)

**Status: the full procurement cycle works end to end — Supplier → Purchase Requisition → Purchase Order → Goods Receipt (which posts real inventory ledger entries) → Supplier Invoice → Supplier Payment → Settlement — in the ERP.** Built on the same explicit-state-machine discipline as Phase 4b's B2B workflow (`apps/api/src/modules/procurement/procurement-status.ts`): every status change is a named, checked action; nothing writes a status directly.

Produced:
- **Seven purchase types** (`GOLD, SILVER, PLATINUM, STONE, FINISHED_JEWELLERY, RAW_MATERIAL, CONSUMABLE`), split into *weight-tracked* (gold/silver/platinum/raw material/stone — ordered and received by grams, priced `fineWeight × ratePerGram` in the gold-trade convention) and *quantity-tracked* (finished jewellery, priced per piece; consumables, priced per unit or left unpriced). A line's `value` is computed server-side and never accepted as input — deliberately **not** `packages/pricing-engine` (that engine resolves a *sales* price to a customer through a rule hierarchy; a purchase line is simply what was agreed with one supplier).
- **Purchase requisitions** (`DRAFT → SUBMITTED → APPROVED → CONVERTED`, or `REJECTED`/`CANCELLED`) — an internal ask, raised before committing to a supplier, that becomes a purchase order once approved.
- **Purchase orders** (`DRAFT → SUBMITTED → APPROVED → PARTIALLY_RECEIVED/RECEIVED`, or `CANCELLED`) — `PARTIALLY_RECEIVED`/`RECEIVED` are *derived* from the lines' own received-so-far figures, applied through the same named-action + derived-target pattern as B2B's sales-order allocate/invoice. Cancelling a partially-received order closes out what's left; what already arrived (and its inventory) stands, untouched.
- **Goods receipt, wired directly into the inventory ledger** (business-rules.md §2.1's rule holds here exactly as it does for a sale): posting a receipt creates real `InventoryItem`s (one batch per weight-tracked line; one `UNIT` piece per finished-jewellery piece; nothing for a `CONSUMABLE` line — it has no weight/purity/fineness, a documented simplification in the `StoneInventory` tradition) and a `PURCHASE_RECEIPT` ledger entry, in the *same* inventory transaction as the receipt document and the purchase order's progress/status update. **Support requisitions:**
  - **Partial receipts** — a line may be received across several goods receipts; each is checked against what's still outstanding.
  - **Over-receipt** is refused (`OVER_RECEIPT`, 409) before anything is written.
  - **Incorrect purity** — receiving at a purity that doesn't match the order is refused (`PURITY_MISMATCH`, 409).
  - **Weight discrepancy** — a scale reading more than 2% off a *stated* `expectedGrossWeight` (what the delivery note claimed for that shipment) needs an explanatory note to post; a genuine partial receipt with no stated expectation is never flagged, since there's nothing to compare it against.
  - **Cancellation** — a purchase order can be cancelled before receipt, or with what's left of a partially-received one.
  A goods receipt is append-only once posted: never edited or reversed (a supplier return, if ever needed, would be a new movement).
- **Supplier invoices** (the supplier's own bill, linked to a PO and the receipts it covers where appropriate) and **supplier payments** — simpler than B2B's customer payments (no maker–checker: `accounting.create_payment` is itself the control, matching the separation of duties already in the role matrix), but the same "paid is always derived from unreversed allocations, never stored" rule, the same racing-allocation guard (`allocationSeq`), and the same all-or-nothing reversal.
- **Two new permissions** (`purchasing.receive`, `purchasing.cancel`, alongside the pre-existing `purchasing.view/create/approve`) — `PURCHASE_MANAGER` gets the full set except money movement (that's `accounting.create_payment`, kept with `ACCOUNTANT`, the same separation B2B payments use); `WAREHOUSE_MANAGER` gets `purchasing.receive`.
- **ERP screens**, using the design system: a purchase dashboard (open requisitions/POs, receipts pending, payables, recent activity), a supplier list with each supplier's live payables position, purchase orders (with a folded-in requisitions panel, line-by-line creation, approve/cancel, and a receive-goods form), goods receipts (list and detail, discrepancies flagged), purchase detail (the PO's own page — lines, totals, linked receipts), and supplier outstanding (ageing, unpaid invoices, record/apply/reverse payments) — five nav entries under **Purchasing**.

**Verified, not claimed:** `pnpm -r typecheck` and `pnpm -r lint` clean across all 9 workspaces; **1190 API tests** (up from 1089: +75 state-machine/line-arithmetic/validation unit tests, +26 HTTP tests covering the full lifecycle and, explicitly, partial receipt, over-receipt, incorrect purity, weight discrepancy and cancellation). One real bug the tests caught before this note was written: the error-code → HTTP-status table (`error-handler.ts`) defaults an unrecognised code to 400, so the new `OVER_RECEIPT`/`PURITY_MISMATCH` errors were silently answering 400 instead of 409 until added to the table.

Not done, deliberately: a **requisition→PO picker in the ERP UI** (the backend supports linking a PO to an approved requisition; the "new purchase order" form doesn't yet offer "start from this requisition" as a shortcut — it's still reachable by entering the same lines again); **supplier returns** (a goods receipt is append-only; a return would be a new, not-yet-built movement); per-supplier price lists or rate contracts; landed-cost allocation (freight/duty spread across lines); GST input-credit tracking on supplier invoices (`taxAmount` is a single entered figure, not a CGST/SGST/IGST breakdown); a supplier-facing portal (this phase is ERP-only, unlike B2B's customer-facing portal).

## Phase 4b — B2B commercial workflow, as explicit state machines (2026-09-22)

**Status: the Phase 4 B2B cycle is rebuilt on named, explicit state-transition rules (not ad hoc status writes), with the approve/convert split, partial allocation and multi-invoice fulfilment, billing addresses, PO attachments, and audited price overrides/discounts/approvals/rejections/credit overrides/cancellations — end to end in both the ERP desk and the portal.** This refines Phase 4 rather than replacing it: same documents, a stricter workflow.

Produced:
- **Explicit business rules, not free-form status writes** (`apps/api/src/modules/b2b/b2b-status.ts`): every transition is a named action — `submit`, `startReview`, `quote`, `counter`, `approve`, `accept`, `reject`, `decline`, `expire`, `convert`, `cancel` for the PO; a parallel set for the quotation; `confirm`, `allocate`, `release`, `invoice`, `cancel` for the sales order — each declared as `{from: Status[], to: Status}` and checked by `checkPoAction`/`checkQuotationAction`/`checkSoAction`/`checkPaymentAction`, which throw a typed 409 (`IllegalB2BTransitionError`) on anything not in the table. A sales order's target status is *derived* from its own numbers (`salesOrderStatusFor({total, allocated, invoiced})`), not stored as a free choice.
- **New status vocabularies**, matching the spec exactly: PO `DRAFT, SUBMITTED, UNDER_REVIEW, QUOTED, NEGOTIATION, APPROVED, REJECTED, EXPIRED, CONVERTED, CANCELLED`; Quotation `DRAFT, QUOTED, NEGOTIATION, APPROVED, REJECTED, EXPIRED, CONVERTED, SUPERSEDED`; Sales order `DRAFT, CONFIRMED, PARTIALLY_ALLOCATED, ALLOCATED, PARTIALLY_FULFILLED, FULFILLED, CANCELLED` (`DRAFT` here means *held for credit*, not a draft document).
- **Approve is split from convert.** `approvePurchaseOrder` only fixes the agreed terms — lines, prices, making charges, discount, tax, total — into `po.approved` at today's rate; it commits nothing. `convertPurchaseOrder` is the credit-enforcement point: it creates the `SalesOrder` from the frozen `approved` terms (`CONFIRMED`, or `DRAFT`/held if credit blocks it). This is new since Phase 4, where approving created the sales order in one step — needed so `APPROVED` (terms fixed) and `CONVERTED` (order created) are genuinely different, audited moments.
- **Partial allocation and multi-invoice fulfilment.** `allocate` reserves whatever stock is available per line (not all-or-nothing) and reports a line-by-line `shortfall`; the order's status (`PARTIALLY_ALLOCATED`/`ALLOCATED`) is derived from the numbers. A new `release` action gives back allocated-but-uninvoiced stock. `invoice` takes an optional `lines: [{lineIndex, quantity}]` to invoice a chosen subset, so one sales order can carry several invoices (`Invoice.sequence`, `SalesOrder.invoices[]`); each line's `progress` (`quantity`/`allocated`/`invoiced`) is shown, not just a single status.
- **Billing address as its own field** (`PurchaseOrder.billingAddress`, `SalesOrder.billingAddress`, `Invoice.billingAddress`) distinct from the shipping address, taken from the customer's own billing address at document creation and frozen from then on (`freezePaths`) — an invoice always shows what it was billed to, not the account's current address.
- **Per-line making charges and discount broken out explicitly** on every `B2BLine` (`unitMaking`, `unitDiscount`, `lineMaking`, `lineDiscount`), visible in both UIs, not folded into the taxable amount alone.
- **PO attachments** (`apps/api/src/modules/b2b/attachments.service.ts`): a `DocumentStorage` port (memory for tests, local-disk in dev/prod) separate from the public media storage; content is *sniffed from its bytes* (PDF/PNG/JPEG magic numbers, XLSX zip signature, sane CSV), never trusted from the filename or `Content-Type`; 5 MB / 10 files per PO; download only through an authorised route (`Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store` — never a public URL); a customer can only remove a file their side uploaded.
- **Draft quotations.** `quote` takes `issue: false` to save a quotation a buyer cannot see yet (excluded from every buyer-scoped read); `issue`/`discard` send it or throw it away. A quotation-expiry sweep (a periodic timer, 60 s in production, plus a lazy refresh-before-every-read) expires stale `QUOTED`/`NEGOTIATION` quotations — and the PO waiting on one — so what's shown is always current.
- **The six audited events the spec named**, each with its own action and content: `B2B_PRICE_OVERRIDE`/`B2B_DISCOUNT_APPLIED` (a target price or a percentage concession, with the standard and agreed price and a now-*mandatory* reason, min 5 characters), `B2B_PO_APPROVED`/`B2B_QUOTATION_APPROVED` (approval, by either path — direct or via an accepted quotation), `B2B_PO_REJECTED`/`B2B_QUOTATION_REJECTED` (rejection, seller or customer side, with the reason), `B2B_CREDIT_OVERRIDDEN` (who, why, the limit, and exactly which reasons were overridden), `B2B_ORDER_CANCELLED`/`B2B_PO_CANCELLED` (cancellation, with what was released and what had already been invoiced).
- **ERP screens** (`apps/erp/components/b2b/*`) updated for all of the above: the approve→convert two-step flow with its own confirmation copy, billing address alongside shipping, a making-charge/discount column, attachment upload/download/remove, per-line allocation/invoice progress, a "release" action, invoicing a chosen subset of lines, and draft-quotation send/discard.
- **Portal screens** (`apps/b2b-portal/**`) updated to match: new status labels and step tracker (`lib/status.ts`), attachments on a purchase order, billing address shown beside shipping, an order's per-line progress table and its (possibly several) invoices, and an invoice's own frozen billing address (not the account's current one).

**Verified, not claimed:** `pnpm -r typecheck` and `pnpm -r lint` clean across all 9 workspaces; **1089 API tests** (up from 847: +246 in a new exhaustive state-machine matrix test — every `(action, status)` pair for the PO, quotation, sales order and payment machines — and +17 new HTTP tests covering attachments, draft quotations, release, partial invoicing, the expiry sweep, and audit-log *content* for each of the six named events); portal and ERP suites unchanged and still green (9 and 106). Two real bugs were caught by the new tests before this note was written: a draft quotation's `issuedAt` collided with its own freeze on issuing (fixed by not re-setting an already-frozen field); a buyer-scoped read did not exclude `DRAFT` quotations, so an unsent draft was visible to the customer (fixed in `b2b-reads.service.ts`).

Not done, deliberately (unchanged from Phase 4 unless noted): **CSV/Excel import**; **invoice cancellation, credit notes and B2B returns**; **e-invoicing (IRN) and e-way bills**; **per-buyer roles and approval limits inside one company**; notifications and email; PDF invoices (a print stylesheet only); ERP screens to *create* a wholesale account or set a product's MOQ / price-on-request flags (API and seed only); price-list administration UI. ## Phase 3.5 — B2C checkout & payments (2026-09-21)

**Status: the full purchase path works end to end against a SANDBOX payment gateway; no real gateway is wired in.** Bag → Address → Delivery → Price verification → Payment → Confirmation, as a guest. Production registers no payment provider, so until one is written the storefront says online payment is unavailable and refuses to hold stock for an order nobody can pay for.

Produced:
- **Orders module** (`apps/api/src/modules/orders`): `Order` (single model, `channel: B2C`), `Payment` (one row per attempt, with refunds), `PaymentEvent` (every webhook, unique per provider event id) and `PriceSnapshot` (append-only). Public API under `/api/store`: `POST checkout/verify`, `POST checkout/orders`, `GET orders/:orderNo`, `POST orders/:orderNo/{payments,cancel}`, `POST orders/:orderNo/payments/:id/{verify,cancel}`, `POST payments/webhooks/:provider`.
- **The backend recalculates everything.** `verify` prices the bag from the catalogue, the metal rate and the stock with the one pricing engine (buyer state from the address → CGST+SGST or IGST recorded; the total never differs), adds the delivery fee the business configured, and lists what blocks an order. Request schemas are `.strict()`: a body carrying a price, discount, total, delivery fee or stock level is refused with 400. The only figure the browser reports is `agreedTotal` — a *check*: if it isn't the server's total the order is refused with `PRICE_CHANGED` and the fresh verification, and nothing is created.
- **Placing an order:** DRAFT with one immutable `PriceSnapshot` per line (every engine input and output, the rate and when it took effect) → pieces held in the ledger (`RESERVATION`, 20-minute hold, chosen so the hold and the order move to PENDING_PAYMENT in **one** transaction) → PENDING_PAYMENT. Idempotency key per attempt: a double-click or lost response yields one order; a reused key with a different bag is refused. Two shoppers racing for the last piece: exactly one gets it.
- **Payment abstraction** (`payments/payment-provider.ts`): orders speak only `PaymentProvider` — `initiate`, `fetchStatus` (the provider, not the browser, is the authority), `parseWebhook` (signature check), `refund`, `cancel`. Success, failure, cancellation, webhook, refund are all supported; a payment only moves forward (PENDING → AUTHORIZED → CAPTURED / FAILED; refunds fold into PARTIALLY_REFUNDED / REFUNDED), one function folds every report in, and the same fact arriving by webhook, by the customer's return and twice is applied once.
- **On capture, in one transaction:** payment recorded, order PAID → CONFIRMED, pieces SOLD (ledger `SALE` tied to the order). If it cannot be honoured (stock gone, order already cancelled/paid, wrong amount, a second payment) the money is **refunded automatically** instead. Cancelling before payment frees the pieces and voids the open payment; cancelling after payment returns the pieces (`RETURN`, awaiting inspection) and refunds in full; after PACKED it's a return. An expiry sweep cancels unpaid orders whose hold ran out — asking the provider first, so someone who just paid keeps their order.
- **Order states** — all twelve (DRAFT … REFUNDED) with the transition graph as data (`order-status.ts`); nothing writes `status` except `moveOrder`, a compare-and-set. Order items, totals, customer, address and price snapshots are immutable at the Mongoose layer.
- **Guest access:** an order is opened with an HMAC token of its id (`X-Order-Token`), re-issuable for a retried request, nothing stored; wrong token = 404. A signed-in B2C customer's order is linked to their user id (no B2C sign-in screen exists yet).
- **Sandbox gateway** (`apps/api/dev-adapters/payment-sandbox.ts`, wired only from `dev:memory` and tests): signed webhooks with event ids, redelivery, asynchronous refunds, a hosted payment page on :4100. `isolation.test.ts` keeps `src/` from importing it.
- **Storefront:** stepper checkout (Address with validation using the API's own schema and an Indian-state list → Delivery from the business's own options → Review with the backend's recalculation, the price promise, and the exact amount on the button), a "price changed — accept the new total" step, redirect to the payment page, a return page that asks *our API* to verify with the provider, and an order page (status, frozen prices and what they were built from, pay/retry, cancel with confirmation, refund status).

**Verified, not claimed:** `pnpm -r typecheck` clean, lint clean, `next build` clean; **746 API tests** (83 new: 70 checkout/payment HTTP tests incl. concurrency, 13 state-machine tests), 46 storefront logic tests (7 new), 249 engine, 106 ERP; a **56-check Playwright run** against the real API and the sandbox page: happy path to CONFIRMED, decline then retry, backing out then cancelling, cancel-and-refund of a paid order, a price change on the review step, another shopper taking the last piece, double-click places once, a second browser cannot open the order, phone layout.

Bugs found by testing:
- **A duplicate webhook delivered at the same instant refunded a payment that had just paid the order** — the losing copy saw "order not payable" and treated the money as unfulfillable. It now re-reads the order and, if this payment paid it, does nothing. Repeated the racing tests six times; stable.
- Two `Order.create` paths raced on the idempotency key; the loser now returns the winner's order.
- The webhook event record raced its own unique index; a duplicate-key error now means "already received".
- A failed gateway call moves the order to PAYMENT_FAILED (retryable) rather than leaving a misleading PENDING_PAYMENT.
- The Playwright script needs a fresh `dev:memory` per run (stock is consumed).

Not done, deliberately: **a real payment gateway adapter** (write one against `PaymentProvider`; nothing here was tested against real Razorpay/Stripe/etc.); staff order screens and the fulfilment transitions PACKED → SHIPPED → DELIVERED, return requests and REFUNDED-after-return (the graph exists, nothing drives it); order emails/SMS; B2C sign-in and order history; a refund that the gateway refuses is recorded on the payment but has **no ops screen to retry** (`payments.refund` is the entry point); shipping charges are a flat, tax-inclusive fee per option (no zones, no weight); a single HSN; the expiry sweep is an in-process timer (move to BullMQ); dashboard Sales/B2B still say *not connected* — orders now exist to feed them; cancelled paid pieces need an ERP inspection before resale; the crash window between "order cancelled" and "pieces returned" isn't reconciled by a job.

Real bugs found and fixed via testing, not just claimed:
- The `postInventoryTransaction` line schema originally restricted `quantityDelta`/`weightDelta` to positive-only values, which made it impossible to represent material *leaving* a batch (e.g. `MANUFACTURING_ISSUE` reducing a gold bar's weight) — caught by the BATCH-item test, fixed to accept signed non-zero deltas.
- Two of my own test files had hand-calculation mistakes in the expected fine-weight values (off in the 3rd decimal place after rounding) — caught by actually running the tests rather than trusting the arithmetic, fixed to match `weight-calculations.ts`'s real output.
- Mongoose 8's `SchemaOptions<T, ...>` generic doesn't structurally unify across different model files even via a shared helper (variance in the `Model`/`Document`/`statics` type parameters) — resolved once in `mongoose.helpers.ts` with a documented double-cast rather than fighting it at all 20 call sites.

**Design-system fixes made along the way** (all in `packages/ui`, discovered via the browser-driven verification below, not by inspection):
- `Button`'s `asChild` path crashed against Radix `Slot` whenever `loading={false}` — the falsy loading-spinner conditional still counted as a second child. Fixed by giving `asChild` its own render path with no spinner injection.
- Seven components called React hooks without `"use client"` (`combobox`, `date-picker`, `currency-input`, `weight-input`, `percentage-input`, `pagination`, `product-gallery`) — fine when only ever used inside already-client pages (Phase 0.5's showcase), but crashed the instant a **Server** Component rendered them directly, which real ERP/storefront pages now do.
- A second, related class: `data-table`, `button`, `table`, `input`, `textarea`, `card`, `badge` attach event handlers to the raw DOM elements they render, which also requires `"use client"` regardless of hook usage — Server Components cannot attach handlers to host elements across the boundary.
- Corollary discovered while fixing the dashboard: once `DataTable` is a Client Component, a Server Component page can no longer pass it column defs containing render functions (functions can't cross the Server→Client prop boundary). The fix is a small local Client Component wrapper at the call site (see `apps/erp/components/recent-orders-table.tsx`, since removed when the placeholder dashboard was replaced — the pattern stands) — a real architectural pattern for this codebase going forward, not a one-off hack, and now the documented approach for any future server-rendered ERP list page.
- `toggleWishlist` called `toast()` (a cross-component `setState`) from inside a `setState` functional updater, which React flags as "setState while rendering" — moved the toast decision out of the updater.
- Added `AnnouncementBar` to the design system (new, for the B2C header) and gave `CartDrawer` optional `title`/`checkoutLabel`/`emptyTitle`/`emptyDescription` props so B2B could reuse it verbatim instead of forking a near-duplicate drawer.
